# F0 — Metamodel: components, relations, evidence

Written 2026-11-13 (Mariam). Revised 2026-11-13 after an external
architecture review (v2), then amended to v2.1 per the reviewer's six
contract clarifications. Status: APPROVED baseline for F1 (reviewer GO
with v2.1 amendments, received 2026-11-13; F1 authorized). This is stage
F0 of the foundation build order in
`CqrsLens_Modeling_Foundations.md` (R0–R4): the component/relation
taxonomy with the evidence rule for every relation.

Sources: the shipped code at `bd49fc3` (CqrsLens 1.1.0) — every "built"
claim below names the type that implements it — and the foundations
document. Where this paper proposes something the code does not do yet, it
says PLANNED and names the stage that would build it (F1/F2). Nothing here
is built yet.

Revision notes (v2): the review found three foundational inconsistencies in
v1 — relations whose endpoints were not components, identity by bare type
name, and one flat evidence shape for all relation kinds — and asked for
tighter semantics on six relations plus explicit F1 gates. Each was checked
against the code before accepting: the relation/identity/evidence fixes are
adopted (§1–§5); the `Wraps` concern was confirmed in code (see §4.3); the
`IsInferred` flag was confirmed to be part of the JSON contract, so
per-fact provenance is specified as additive (§5.3). The direction,
evidence-first discipline, exclusions, and §9 defaults are unchanged.

Revision notes (v2.1): six contract clarifications, no scope change:
(1) endpoint identity is mapping-level, covering Minimal API lambdas with
no declared method symbol (§2); (2) a `Type` reference kind for
non-component dispatch senders (§3.2, §4); (3) deduplication uses the
ordered `Via` path, not a set (§5.1); (4) static evidence boundaries
stated explicitly — registrations do not prove runtime resolution, traced
access does not prove execution (§4.4, §7); (5) `Wraps` applicability
tightened around registration, generic constraints, and unestablishable
cases (§4.3); (6) a `PackageReference` alone never identifies an external
type (§3.2, §9.3).

## 1. The model in one paragraph

CqrsLens generates a static, evidence-backed model of an application's
architecture. The model consists of discovered projects, inventoried
components, typed references, and directed relations. A component is an
architectural participant whose role is established by source evidence. A
typed reference identifies a symbol that may participate in a relation
without necessarily qualifying as an inventoried component. Each relation
describes a statically justified fact between addressable nodes and retains
one or more evidence occurrences, including the rule that admitted it.
Inferred properties, unresolved references, and ambiguous resolutions
remain explicitly distinguishable from proven facts. The model is
generated from source, never hand-edited, and serves as the authoritative
data foundation for reports, diagrams, queries, documentation, checks, and
future comparisons.

Today the tool builds `AnalysisResult`: flat lists of shapes plus three
separate edge lists, renders a document, and discards the model. The
metamodel keeps every one of those facts and reorganizes them around one
spine:

**project → component → relation.**

The CQRS shapes stop being the spine and become one component family among
several. What does not change: the model is generated by the tool and read
by developers, never hand-edited (R0); every relation carries its evidence;
what cannot be proven is recorded as unproven, never drawn as fact.

## 2. Identity

A bare dotted type name does not identify a participant: two projects can
declare the same namespace and type name, and a generic declaration is not
its constructed usages. Identity is therefore layered. (These are
conceptual identities for the model contract, not proposed type names.)

- **ProjectId.** The root-relative path of the `.csproj` file. Unique in a
  scan by construction: two projects cannot share one project file.
- **SymbolId.** ProjectId + qualified declaration identity: namespace,
  containing types, name, and generic arity. Composed by the single
  implementation `TypeFullName`, extended with the declaring project.
  Two shapes with the same simple name in different namespaces — or the
  same qualified name in different projects — are different symbols.
- **ComponentId.** The identity of one inventoried participant: the
  SymbolId of the declared symbol it is inventoried from. One declared
  symbol yields at most one component; see §2.1 for multiple roles.
- **EndpointId.** A mapping-level identity: ProjectId + the mapping site
  (the source location of the mapping expression) + a stable
  discriminator when one site declares several mappings (ordinal within
  the site, in source order). Route and verb are properties of the
  endpoint, never its identity: a route can be inferred (§5.3), one
  method can carry several mappings, and a Minimal API lambda need not
  have a declared method symbol at all — the mapping site is what exists
  in every case. Endpoints are mapping-derived components, not
  symbol-derived ones, so mapping-level identity does not contradict
  the one-component-per-symbol rule (§2.1), which governs
  symbol-derived components.

Further rules:

- **Nested types.** A symbol declared inside another type carries its
  containing types (`HandlerInfo.ContainingTypes`); the qualified name
  includes them.
- **Generics.** Identity follows the `ServiceResolution` scheme: a
  non-generic type is its full name; an open generic keeps its arity
  suffix (``IPipelineBehavior`2``); a closed generic appends substituted
  arguments. A generic declaration and its constructed usages are
  different identities; a closed generic may be a meaningful resolution
  target without being a separate source-declared component.
- **Non-concrete shapes.** An open generic request is never dispatched
  as-is, so it is not a component — but its identity is recorded
  (`AnalysisResult.NonConcreteRequestNames`) so that a validator targeting
  it is not misreported as an orphan. The rule generalizes: a shape that
  cannot be a runtime participant is recorded, not modelled, and its
  record explains the gap it would otherwise cause.
- **Locations.** Every component and evidence occurrence carries a source
  location (`SourceLocation`: file, line, column, root-relative) when the
  evidence has one. Evidence without a location must say why (e.g. a
  project reference, whose evidence is the `.csproj` file itself).
- **Determinism.** Repeated scans of unchanged source produce equivalent
  identities and relations. Identity construction uses nothing
  scan-order-dependent; ordering of model contents is deterministic (the
  existing rule: first location in deterministic scan order).

### 2.1 One symbol, multiple roles

A class may have more than one architectural role: a class can be both a
service and a repository; a background worker can also handle
notifications. The model records **one component per declared symbol, with
an evidenced set of roles** — not one component record per role. Duplicate
nodes would double-count dependencies and split queries. Each role on the
set carries its own role evidence (§3); a role without evidence is not
added. A component's roles are a property of the component, and views may
filter by role without duplicating the node.

## 3. Nodes: components, structural nodes, typed references

A relation connects two addressable nodes. Not every addressable node is a
component: an interface can participate in a relation without being falsely
classified as a service, and a method can be a call target without being an
architectural participant. The graph has three node kinds:

1. **Structural nodes** — containers: projects and layers (§6).
2. **Components** — inventoried participants with an evidence-derived role
   (§3.1). "A class exists" is not a role.
3. **Typed references** — addressable symbols that participate in
   relations without qualifying as components (§3.2).

### 3.1 Components

The roles below are the Tier 1 set from R1; each names its detection
evidence and its status in 1.1.0. A component carries its ComponentId, its
evidenced role set (§2.1), its declaring project, and its location.

| Component kind | What it is | Role evidence | Status in 1.1.0 |
|---|---|---|---|
| Request | A command/query message contract | Implements a request marker (`IRequest`, configured `--markers`), including source-declared wrappers | Built (`CqrsRequest`) |
| Handler | A class handling one request | Implements a handler marker for a resolved request | Built (`HandlerInfo`) |
| Notification | A published message contract | Implements `INotification` / `IDomainEvent` markers | Built (`CqrsNotification`) |
| NotificationHandler | A class handling a notification | Implements a notification-handler marker | Built (`NotificationHandlerInfo`) |
| Validator | A class validating a request | Implements a validator marker for a resolved request | Built (`ValidatorInfo`) |
| Behavior | A pipeline behavior around requests | Implements a behavior marker; order from its registration site (null when the site cannot be resolved — assembly scanning, external registration, ambiguous match) | Built (`BehaviorInfo`) |
| DbContext | An EF Core context class | Derives from `DbContext`, including primary-constructor form | Built (`DbContextInfo`) |
| Entity | A type mapped as EF data | `DbSet<T>`, navigation, annotation, or Fluent configuration | Built (`EntityInfo`) |
| Endpoint | An HTTP entry point | Controller action, Minimal API mapping, or FastEndpoint, with route + verb | Built, partial (`EndpointInfo`; see §3.3) |
| Service | A class injected and called through an interface or directly | Constructor injection + call sites, or a DI registration naming it | Planned (F2). Today services exist only as edge targets and resolution candidates, not as inventoried components |
| Repository | A service whose role is data access | Injects a DbContext / is named by a repository convention *and* touches data | Planned (F2). Role must come from evidence (DbContext use), not from the name alone |
| Controller | A class exposing endpoints | Derives from a controller base / carries endpoint attributes | Planned (F2). Today only its endpoints are inventoried |
| BackgroundWorker | A hosted background class | Derives from `BackgroundService` / implements `IHostedService` | Planned (F2). No detection exists today |

### 3.2 Typed references

| Reference kind | What it identifies | Identity | Used by |
|---|---|---|---|
| Interface | A service contract a relation resolves through | SymbolId of the interface declaration (open/closed per §2) | `ResolvesTo`, `UsesDataResolved`, `Calls` (via) |
| Method | A method invoked by a call | Declaring type SymbolId + method name | `Calls` |
| Member | A `DbSet` or entity member touched by data access | Declaring type SymbolId + member name | `TouchesData` |
| Type | An ordinary source class that participates in a relation without an inventoried role (e.g. a service class that dispatches a request) | SymbolId of the class declaration | `Dispatches`, `Publishes` (sender) |
| External | A type named by evidence but declared outside the scan (e.g. an external implementation named by a registration) | As written in the evidence, labelled external | `ResolvesTo` |
| Unresolved | A symbol the evidence names but the scan cannot resolve | As written, with the reason it could not resolve | Unproven populations (§5.4) |

A `PackageReference` names a package, not a type: it never by itself creates an `External` type reference. Package references are project-level facts (`ProjectInfo.PackageReferences`); an `External` type reference requires evidence naming the type itself.

Method identity is declaring type + name. Overloads are not distinguished
in Tier 1: a `Calls` relation claims "a call to a method of this name on
this type", and overload resolution is out of scope. This matches today's
`ServiceCallEdge`, which carries the method name without a signature; the
limitation is stated, not hidden.

### 3.3 Endpoints: built, with an honesty flag

`EndpointInfo.IsInferred` marks routes or verbs guessed from a naming
convention (an endpoint group's class name, a verb implied by
Query/Command) rather than read from source. Inferred endpoints stay in
the model, but every view must flag them so no consumer treats a guess as
a fact. F1 refines this to per-fact provenance (§5.3) — a verb can be
declared while its route is inferred — as additive data: the existing
`Inferred` JSON field stays intact.

## 4. Relations

A relation is a directed, statically justified fact between two addressable
nodes. The admission rule, from R1, is absolute: **a relation type with no
evidence rule does not enter the model.** Each relation below names its
evidence rule — the exact static observation that justifies drawing it —
and its status. Endpoints in the table are node kinds from §3, not only
components.

| Relation | From → To | Evidence rule | Status |
|---|---|---|---|
| References | Project → Project | A `ProjectReference` in the `.csproj`, resolved to a project in the same scan (`ReferenceNames`) | Built |
| Serves | Request → Handler | Handler marker implementation linked by full name (simple-name fallback only when unambiguous) | Built (`FlowEdgeKind.RequestToHandler`) |
| Validates | Validator → Request | Validator marker implementation linked the same way | Built (linking; no flow-edge kind — see §4.1) |
| Wraps | Behavior → Request | See §4.3: registration + applicability evidence, not mere discovery | Partial (see §4.3) |
| Dispatches | Component / Type ref → Request | A call site whose target type statically resolves to an inventoried request, classified by the resolved contract's kind (§4.4). The sender may be any component or an ordinary source class (`Type` reference, §3.2) | Built (`FlowEdgeKind.EndpointToRequest`, `HandlerToRequest`; `DispatchCallSite` for any sender) |
| Publishes | Component / Type ref → Notification | A call site whose target type statically resolves to an inventoried notification, classified by the resolved contract's kind (§4.4) | Built (`FlowEdgeKind.HandlerToNotification`) |
| HandlesNotification | Notification → NotificationHandler | Notification-handler marker implementation linked to the notification | Built (linking) |
| UsesData | Handler → DbContext | The handler references a discovered DbContext type directly | Built (`FlowEdgeKind.HandlerToDbContext`) |
| UsesDataResolved | Handler → DbContext, via interface | The handler injects an interface; the service-resolution index resolves it to a DbContext implementation | Built (`FlowEdgeKind.HandlerToDbContextResolved`, `ResolvedEdge`) |
| ResolvesTo | Interface reference → Implementation | The service-resolution index: a single declaring class, an explicit DI registration, or both. Ambiguous or empty candidate sets resolve to nothing (fail-closed). Semantics per §4.4 | Built (`ServiceResolution`; MS-DI + Autofac registrations only) |
| Calls | Component → Method reference | A method-body call whose target expression is *exactly* an injected member (`_repo.GetAsync(...)`); calls on a property's return value, a local, a parameter, a `new` object, a static, `base`/`this`, or an unresolved interface are not edges. The resolved implementation, when known, is carried in evidence | Built (`ServiceCallEdge`) |
| TouchesData | Handler → Entity / Member reference | Deep-slice observation: the handler's dependencies and body touch a `DbSet` or entity, possibly through a chain; the resolution path is carried in evidence (§4.4) | Built (deep slice; recorded on handler/request, not yet an edge kind — see §4.1) |
| Relates | Entity → Entity | Navigation property, foreign key, data annotation, or Fluent API configuration, with cardinality | Built (`EntityRelationshipInfo`, `OneToOne`/`OneToMany`/`ManyToMany`) |
| Exposes | Controller → Endpoint | The endpoint is declared on the controller | Planned (F2; needs Controller as a component) |

### 4.1 Two facts that are relations but have no edge kind yet

Validates and TouchesData are proven facts in 1.1.0 — linking and the deep
slice compute them — but they live as lists on shapes (`CqrsRequest.Validators`,
`HandlerInfo.TouchedEntities`) rather than as edges in any edge list. F1
promotes them to relations in the unified relation list (§8) with no change
to any count, check, or report field: the promotion is a reorganization, not
a new claim. No new detection is involved, so no new ground truth is needed
for them.

### 4.2 Relations that stay out

- **Runtime behaviour.** Anything requiring execution: actual call counts,
  actual dispatch at runtime, actual DI scope behaviour. The model is
  static evidence only.
- **Dynamic dispatch beyond evidence.** A dispatch-looking call whose
  target cannot be statically resolved is an `UnresolvedDispatch`, counted
  and reported — never an edge.
- **Convention-based DI (ABP).** Registration by assembly-scanning
  convention has no per-type evidence in source, so it stays out on the
  same rule as Phase 7. If a future corpus shows a convention with
  checkable per-type evidence, that is a re-charter, not an extension.
- **Materialized aliases.** A query reading of an existing relation (e.g.
  "endpoint enters through dispatch") is a view, not a second relation.
  Materializing it would double-count one fact in traversals and counts.
- **Tier 2 (R1).** Messaging (publish/consume over MassTransit/Wolverine
  conventions, integration events), external integrations (typed
  `HttpClient`, gRPC clients), configuration/feature surface. Each needs
  its own evidence rule and its own hand-audited corpus before admission.

### 4.3 Wraps: discovery, registration, and applicability are three facts

A behavior class discovered in source, a behavior named by a registration,
and a behavior proven to wrap a specific request are different facts, and
the model must not collapse them:

- **Discovery.** The behavior component exists (marker implementation).
  No request is implied.
- **Registration.** A registration site names the behavior, with its
  ordinal among registrations at that site (`BehaviorInfo.RegistrationOrder`,
  null when the site cannot be resolved). Registration is evidence about
  the pipeline, not yet about any one request.
- **Applicability (`Wraps`).** A `Wraps` relation from a behavior to a
  request requires applicability evidence, evaluated in this order:
  (1) the behavior is closed over that specific request (a marker
  binding naming the request) — it applies to that request; (2) the
  behavior is registered as an open generic AND its generic constraints,
  if any, are satisfied for the request — it applies to requests in
  scope, with the registration as evidence; (3) otherwise, no `Wraps`
  relation. Cases where applicability cannot be established —
  assembly-scanning registration with no per-type evidence, external
  registration, generic constraints that cannot be evaluated statically,
  or no registration site at all — are recorded in the unproven
  population (§5.4), never edged. A discovered-but-unregistered
  behavior gets no `Wraps` relation.

**Known gap (verified in code):** today's per-request sequence rendering
draws from the whole discovered behavior set (`RequestSequenceBuilder`
flattens `result.Behaviors` for every request; no per-request
applicability rule exists in the code). The rendering therefore shows
behaviors whose applicability to that request is unproven. F1 does not
silently change this rendering — the frozen-output gate (§8) forbids it.
F1 records the gap, models `Wraps` under the rule above, and aligning the
rendering to the rule becomes an intended, recorded change for Abdullah to
approve separately.

### 4.4 Tightened semantics

- **ResolvesTo: candidate vs binding.** A unique implementation in the
  scanned source is a useful static candidate, but it does not prove the
  runtime container will resolve it. The relation kind stays `ResolvesTo`;
  the evidence (§5) carries the distinction: declaration-only means
  *statically resolved candidate*; an explicit registration means
  *declared binding*; both means *confirmed*. `ServiceResolutionSource`
  already records which; F1 states the semantics instead of leaving them
  implicit. Nothing about `ServiceResolution`'s fail-closed behaviour
  changes.
- **Static facts, not runtime proofs.** A DI registration — even an
  explicit one — does not prove the runtime container resolves that
  implementation; `ResolvesTo` is a static fact about declarations and
  registrations, and its evidence says which. Traced data access does
  not establish actual execution; `TouchesData` proves a static path
  exists through the code, not that the access runs. The model
  describes code structure, never runtime behaviour.
- **Dispatches vs Publishes: classified by the resolved contract.** The
  method name alone never classifies a call. A call site is `Dispatches`
  when its resolved target is a request, `Publishes` when its resolved
  target is a notification (`DispatchTargetKind`), whatever the method is
  named. Request dispatch and notification publication are different
  activities and stay different relation kinds.
- **UsesData vs TouchesData: reference vs access.** `UsesData` proves the
  handler references a DbContext type (directly, or through a resolved
  interface). `TouchesData` proves the handler's execution path touches a
  `DbSet` or entity — possibly through a chain (handler → injected
  interface → resolved implementation → `DbSet`). The two are not
  interchangeable, and deep-slice results must preserve the distinction:
  a type reference is not proof of data access, and data access through a
  chain must carry the chain in its evidence (§5.2).

## 5. Evidence

### 5.1 One logical relation, many occurrences

A relation is one logical fact. The observations supporting it are
evidence occurrences, and one relation can have many: a handler calling
the same repository method at three call sites is one `Calls` relation
with three occurrences — not three relations. The model exposes both
numbers, because they answer different questions (§5.5).

Today's `ServiceCallEdge` already deduplicates to one edge, keeping only
the first call site in deterministic scan order; the other sites are
dropped. F1 keeps that edge (frozen output) and records every occurrence
additively, so no observation is lost and no count changes.

**Deduplication key.** A logical relation is unique by (kind, from, to,
ordered `Via` path, method-if-any). The `Via` path is ordered: two
dependency chains reaching the same target through different
intermediates are different relations, even when their endpoints match.
Two observations with the same key are occurrences of one relation;
observations differing in any key element are different relations.

### 5.2 The evidence record

Evidence is a structured record, not four flat fields — because the old
`Source` (declaration / registration / both) is a service-resolution
concept that cannot describe an HTTP mapping, a method call, an EF
relationship, or a project reference. Each occurrence carries:

| Field | Meaning |
|---|---|
| Rule | The evidence rule from §4 that admitted the relation, named on the occurrence. Any relation can answer "which rule put you here?" |
| Origin | Where the observation came from: declaration, registration, call site, mapping/attribute, project file, configuration. One vocabulary for all relation kinds |
| Location | The source location of this occurrence, when it has one |
| Via | The ordered intermediates the fact passes through (interfaces, contracts) — a list, not a single hop, so a transitive path (`Handler → injected interface → resolved implementation → DbSet`) is fully justified |
| Strength | Proven (direct static observation), Resolved (through the resolution index or a registration), or Inferred (convention/guess, labelled — see §5.3) |

The 1.1.0 code already carries location and a single `Via`
(`ResolvedEdge.Via`, `ServiceCallEdge.Via`); F1 generalizes `Via` to the
ordered path and adds rule, origin, and strength uniformly. All of it is
additive data: it changes no count, check, or report field.

### 5.3 Strength is per-fact, not per-component

Provenance attaches to the individual inferred fact. An endpoint's HTTP
verb can be explicitly declared while its route is inferred; a layer
assignment can be configured for one project and guessed for another.
One boolean per component (`IsInferred`) cannot express that. F1 records
strength per fact (per property, per assignment) as additive data and
keeps the existing component-level flags intact — `Inferred` is part of
the JSON contract (`JsonEndpoint.Inferred`) and stays exactly as it is.
A check whose conclusion depends on guessed input (e.g. a layer
violation resting on a guessed layer) must identify that dependency in
its finding; a CI failure must never rest on a guess without saying so.

### 5.4 Unproven populations are first-class

The model records what it could not prove, separately from relations, so
that absence of an edge is never ambiguous between "proven absent" and
"could not tell":

- `UnresolvedDispatch`: dispatch-looking calls with unresolvable targets.
- Ambiguous resolutions: interfaces whose candidate set could not be
  narrowed (`ServiceResolution.IsAmbiguous`, no implementation chosen).
- Ambiguous links: shapes with multiple candidates and no local/`using`
  match, reported as `AmbiguousContract` / `AmbiguousLink` diagnostics.
- Unresolved contracts/entities: wrappers, entities, and navigations the
  scan could not resolve to source, each with its own diagnostic code.

A view may show these populations (counts, captions); it must never render
them as edges.

### 5.5 Facts vs observations

The unified model exposes the distinction instead of forcing every
consumer to interpret an edge list as both a list of facts and a list of
occurrences. Relation counts answer "how many distinct dependencies?";
occurrence counts answer "how many places prove them?". Views, checks,
and diffs state which they show. This also makes deduplication, evidence
inspection, incremental comparison, and future architecture diffs
predictable: two scans of the same source produce the same logical
relations, and a diff compares logical relations first, occurrences
second.

## 6. Containment: projects and layers

- **Project contains component.** A component belongs to the project that
  declares it (its ProjectId; the declaring project's directory for
  locations). A component declared in no scanned project is not in the
  model.
- **Layer contains project.** Layers group projects. Today a layer is
  name-guessed unless the user configures overrides
  (`ProjectInfo.Layer`, default `"Other"`;
  `AnalysisResult.HasConfiguredLayers`). The guess is a heuristic, and the
  model must be honest about it: **F1 adds per-assignment provenance —
  configured vs guessed** — following the §5.3 pattern. A guessed layer is
  shown as guessed in every view that uses it, including the
  layer-violation check's inputs. The check itself does not change; only
  the honesty of its input is now visible. Provenance is additive data:
  existing classifications and check results do not move (see the
  compatibility rule in §8).
- **No deeper nesting in Tier 1.** Namespaces and folders are location
  context, not containment levels. If a later stage needs module
  groupings, they arrive as declared intent (R4), not as inferred
  structure.

## 7. What the model refuses

Restating §4.2 as model law, because the widening will tempt each of these:

1. No relation without an evidence rule. No exceptions for "obvious" cases.
2. No runtime facts. No execution, no profiling data, no production traces. Registration is not resolution; a traced path is not an executed path.
3. No hand edits. The model is generated; human input is intent (R4),
   checked against the model, never merged into it.
4. No silent promotion of weak evidence. Inferred, guessed, and ambiguous
   facts carry their label into every view.
5. No convention-based resolution without per-type evidence. ABP stays out.
6. No materialized aliases. One fact, one relation; readings of it are views.

## 8. Migration: today's AnalysisResult becomes the spine (F1 preview)

F1 reorganizes; it does not re-detect. The mapping:

| Today (1.1.0) | In the spine |
|---|---|
| `Projects` | Structural project nodes |
| `Requests`, `Handlers`, `Validators`, `Behaviors`, `DbContexts`, `Notifications`, `NotificationHandlers`, `Endpoints` | Components, one family each, keeping every field; roles become the §2.1 role set |
| `FlowEdges`, `ResolvedEdges`, `ServiceCallEdges` | One relation list; each entry keeps its kind, endpoints, `Via`, location, and gains the §5 evidence record |
| `ServiceResolutions` | The resolution index, unchanged in content; `ResolvesTo` relations read from it, with candidate-vs-binding semantics (§4.4) |
| `DispatchCallSites`, `UnresolvedDispatches` | Dispatch evidence + the unproven population, unchanged |
| `Checks`, `Diagnostics` | Findings over the model, unchanged in content |
| Linking lists on shapes (`CqrsRequest.Handlers`, `HandlerInfo.Dependencies`, …) | Derived views over relations, computed the same way; kept as properties during F1, removed only when every consumer reads relations |

**F1 acceptance gates.** The migration promise becomes concrete conditions,
each checked by the F1 verification (same staged-brief discipline as
Phases 6–7):

1. **Legacy parity.** Every existing check, diagnostic, and frozen metric
   matches the 1.1.0 baseline; the frozen question set holds exactly.
2. **Identity uniqueness.** No two distinct inventoried participants share
   a ComponentId; no two endpoints share an EndpointId.
3. **Evidence completeness.** Every admitted relation has a valid rule
   and at least one traceable evidence occurrence.
4. **No invented certainty.** Ambiguous resolutions and unresolved
   dispatches never become proven edges; inferred facts keep their
   strength label in every view.
5. **Deterministic output.** Repeated scans of unchanged source produce
   equivalent identities, relations, and occurrences.
6. **Bidirectional migration parity.** The legacy edge lists can be
   projected from the unified model without losing supported facts or
   changing their semantics — and the unified model can be built from a
   scan without the legacy lists.

**Compatibility rule.** Provenance and evidence data are additive: they
appear in new fields and sections, and existing classifications, check
results, and report output do not move. Where §6 requires guessed-layer
provenance to be visible and this section requires frozen output to hold,
both are satisfied by addition, never by altering an existing field's
meaning. The JSON contract evolves additively only (R2): existing
sections keep their names and fields; the unified relation list appears
as an additive section, and the old edge sections remain until the public
schema ships at F4.

**Known gap carried into F1.** The `Wraps` rendering gap (§4.3): the
sequence rendering shows all discovered behaviors per request. F1 records
it and models `Wraps` under the stricter rule; aligning the rendering is
a separate intended change, not part of the migration.

## 9. Decisions with defaults

Defaults unless Abdullah vetoes or amends — the same pattern as the
foundations recommendations.

- **§9.1 Endpoints stay components, controllers join them.** An endpoint
  is the HTTP fact users query ("which routes hit this handler?"); demoting
  it to a controller attribute would lose that. Controllers become
  components in F2 and `Exposes` links them. Endpoint identity follows
  §2 (method + mapping site), never the route. Default: keep
  `EndpointInfo` as a component kind.
- **§9.2 Behaviors stay a family, not pipeline steps.** A behavior is a
  class with a registration order, and the behavior chain is a view over
  discovered behaviors ordered by registration. `Wraps` relations follow
  the stricter applicability rule (§4.3). Default: no separate "pipeline
  step" kind.
- **§9.3 External types are typed references, never components.** A
  registration naming an external implementation appears as an `External`
  reference (§3.2), labelled, where the evidence names the type. A package
  reference alone never identifies a type. An external reference never
  gets a role, a layer, or a place in a diagram's component set.
- **§9.4 Layers keep guessing, with per-assignment provenance.** Removing
  the guess would break every existing report's layer diagram for users
  without config. Default: keep name-guessing, add the
  configured-vs-guessed flag per assignment (§6), and show guessed layers
  as guessed.
- **§9.5 One component per symbol, roles as a set.** A class with two
  roles is one component with two evidenced roles (§2.1), not two nodes.
  Default: roles never multiply nodes.

## 10. What F0 does not decide

- Tier 2 admission (messaging, external integrations, configuration
  surface): each needs its own evidence rule + corpus, chartered
  separately after Tier 1 proves out.
- The intent layer's file format and check set (R4): decided at F3, when
  the docs export needs it.
- The public schema's field-level stability promises (R2): decided at F4,
  after one full widening cycle.
- The non-CQRS corpus for F2 (controller → service → repository): selected
  and hand-audited before F2 building starts, per the proof discipline in
  R1. F0 notes the requirement; it does not pick the corpus. The corpus
  must contain negative cases: similarly named services that are not
  used, unresolved interfaces, ambiguous registrations, and indirect
  calls that cannot be proven — those tests are what validate the
  evidence discipline.
